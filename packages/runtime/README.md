# Local optimizer runtime

Standalone TypeScript library and `optimizer` CLI. Node.js 24.18.x required. SQLite is built into Node.js. The only runtime dependency is Zod for boundary validation.

See the repository README for goal syntax, CLI workflow, trust boundaries, and the demonstration. This package owns goal/context intelligence, events, decision policies, persistence, and verification. Adapters and optional MCP tools call this API; they do not own optimizer state.

```js
import { Runtime } from '@optimizer-layer/runtime';

const runtime = new Runtime('/absolute/project');
try {
  const session = runtime.start({
    request: '- R1: parseCount handles numbers\nAcceptance R1: parseCount passes independent checks',
    checks: [{ id: 'acceptance', requirementIds: ['R1'], argv: ['node', '/trusted/acceptance.mjs'], timeoutMs: 5000 }],
  });
  const context = runtime.retrieve(session.id);
  runtime.assess(session.id, {
    kind: 'sufficient',
    rationale: 'Explain why these sources cover the requirement and what uncertainty remains.',
    itemIds: context.items.map(item => item.id),
  });
  runtime.review(session.id, {
    kind: 'accept',
    goalVersion: runtime.get(session.id).goal.version,
    rationale: 'The requirement and acceptance preserve the requested numeric parsing behavior.',
    itemIds: context.items.map(item => item.id),
  });
  // Honor runtime.next(session.id) before further work.
} finally {
  runtime.close();
}
```

An explicitly read-only `new Runtime(project, { readOnly: true })` opens an existing store without initialization or measurement writes. Mutating operations fail. Normal read operations such as status/next are instrumented in writable mode.

Verification checks are trusted, operator-selected argv commands. Register them separately from goal text. They run with this process's privileges and environment; this library is not an arbitrary-command sandbox. Referenced verifier files are pinned; add `artifactFiles: ["/trusted/helper.mjs"]` for helper dependencies not visible in argv. The runtime computes their digests. Changed artifacts require a new operator-registered contract. The current Node executable is trusted as part of the optimizer runtime.

Single-host transactions serialize state and checks. A check holds a write transaction for its bounded duration (at most 10 minutes); other writers fail after a two-second busy wait. No automatic retry executes a command twice. Reads/replay load the session's full event history; this slice targets bounded coding tasks.

Measurements separate registered child-process duration from measured library operation time. Measurement persistence and process startup are not fully included; CLI wall-time measurements in the demonstration capture process overhead separately. Token counts remain unknown when the host supplies none.

Project commands for the Claude Code hooks. With opt-in hooks (the default install) a folder is a project once the user runs `enable`; with always-on hooks any folder is a project. On first use the runtime creates `.optimizer/` (0700) for runtime data only and the per-user record `$XDG_CONFIG_HOME/optimizer-layer/projects/<sha256 of the canonical root>.json` (default under `~/.config`, 0600) holding the hook token, approved checks with pinned artifacts, pending proposal, opt-out flag and active session pointer. Anything inside the project, including a committed `.optimizer/project.json`, is never trusted. It records the root in `optimizer-layer/projects.json` (atomic, deduplicated, rebuilt if corrupt), and adds `.optimizer/` to the enclosing repository's `.git/info/exclude` once. `prompt --file F` appends a hook-captured user prompt to `.optimizer/prompts.jsonl` with an HMAC made with the per-user token; once the per-user record exists it requires `OPTIMIZER_HOOK_TOKEN`, and it returns `{id, checkApproved}`. Rows without a valid HMAC carry no authority. `propose-check --check CMD [--check CMD ...] [--timeout-ms N]` stores a pending proposal with a random four-hex-digit code, replacing an earlier one. A token-checked capture whose text contains `approve check CODE` (case-insensitive, whole words) for the pending code makes those checks the project checks, pins verifier artifacts and clears the proposal; nothing else activates it. `enable [--check CMD ...] [--timeout-ms N] [--yes]` turns the project on, records `optedIn: true` (the flag opt-in hooks require) and creates `.optimizer/`; with `--check` it sets checks directly, without it the current checks (none at first) are kept so the agent can propose one, and `--yes` accepts a `package.json` test script as `npm test`. `disable` opts the project out. Check commands are split into argv without a shell, shell metacharacters are rejected and argv[0] is resolved to an absolute path. `start` takes no `--checks` once a project has a per-user record, re-validates stored argv with the `enable` rules, and `check` runs only argv that matches a currently approved check (refused entirely when the project is opted out; folders without a per-user record keep the explicit `--checks` behaviour, so use those only in trusted directories). A session reaching verified `complete` clears the active pointer. `runtime.sqlite` and its `-wal`/`-shm`/`-journal` companions are refused when they are symlinks: each approved check covers every requirement of the new goal, and without approved checks it fails naming `propose-check`. The session becomes the project's active session, and an unfinished active session requires `--replace` (recorded as `session.replaced` on the old session). `current` returns `{enabled, checks, pendingChecks, sessionId, action, summary}` with a summary of at most 2,000 characters. `resolve --source prompt:ID` resolves a human question from a captured row as a whole message. Each row has its own digest, so later prompts keep earlier decisions fresh while editing a row makes it stale. Rows not captured by the hook, or not from the user, carry no authority. The prompt log is capped at the 4 MiB transcript limit. `runtime.sessions()` lists session IDs newest first.

`optimizer dashboard [--port N]` (default 8790, `0` for a free port) serves a read-only page and JSON endpoint on `127.0.0.1` for every registered project. It requires a random per-start token and a `127.0.0.1:PORT` or `localhost:PORT` Host header, opens each store with `readOnly: true`, and never returns captured prompts, resolved answers, check output, or the hook token.

## Enforced lifecycle controller

`controller.ts` holds the pure workflow policy (no I/O, no LLM); `Runtime` persists its results. See [the design](../../docs/superpowers/specs/2026-10-26-enforced-lifecycle-design.md).

- **Phases.** Every checkpoint command (`start`, `history`, `retrieve`, `assess`, `resolve`, `review`, `check`, `reconsider`, `claim`, `verify`) records a `workflow.transitioned` event `{from, to, cause}` when the derived phase changes, so the current phase replays from events: `requested → contract-proposed → under-review → context-check → ready → executing → reconsidering → verifying → verified | recovery | blocked`. Reads never record a phase, except that the gate records `ready → executing` when it allows the first protected action. Sessions persisted before phases have no `phase` until their next checkpoint.
- **Decisions.** `decide [--session ID]` returns `{decision, reason, requiredBy, phase, needsHuman, action}` with `decision` one of `PROCEED`, `RETRIEVE_CONTEXT`, `INVESTIGATE`, `ASK_HUMAN`, `REVIEW_CONTRACT`, `RUN_VERIFICATION`, `REQUEST_RECONSIDERATION`, `BLOCK_ACTION`, `COMPLETE`, derived from `nextAction` (unchanged) plus the recorded phase. `requiredBy` is `agent`, `human` or `none`. Without a session it defaults to the active one.
- **Gate.** `evaluate(state, action, {managed, available})` takes a tool call classified as `read`, `protected`, `verification` or `control`. Read, Grep, Glob and WebFetch are never gated. Edit, Write, MultiEdit and NotebookEdit are protected. Bash commands are classified in `bash.ts`. The command is first split into shell words and segments (`&&`, `||`, `;`, `|`, `&`, newline), with quotes honoured. Anything the tokenizer cannot represent exactly is protected: redirections (except exactly `2>&1`, `1>&2`, `>&2` and `>/dev/null`/`2>/dev/null` followed by a space, separator or end), `<`, command or process substitution, `$` outside single quotes, backslashes, subshells, unbalanced quotes, and words spliced from quoted and unquoted pieces (`--out""put`). Every segment must then name an allowlisted program, and that program's flags must pass its own allowlist:
  - Any flags are allowed for `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `pwd`, `which`, `echo`, `cd`, `stat`, `diff`, `du`, `realpath`, `basename`, `dirname` and `true`, which have no output-file, exec or in-place flags.
  - `rg` allows only listed search and format flags (no `--pre`).
  - `find` allows only test, traversal and `-print` primaries.
  - `git` allows `status`, `diff`, `log` and `show` with listed flags (no `--output`, `--ext-diff`, `--textconv`, `-c`), and `git branch` with listing flags and no operands.
  - `sed` must be exactly `sed -n ADDRp FILE...`.
  - `tree` and `file` are not allowlisted (they have output flags).
  - Unquoted globs make flag-sensitive programs protected, since a glob can expand to a file named like a flag.
  - `optimizer current|next|status|events|metrics|decide|gate|experiences` are reads.

An approved check argv is `verification`; other `optimizer` checkpoint commands are `control`. Programs named by path and anything unknown are protected. Writes to `.optimizer/` (except `drafts/`) and to the per-user store are always denied, and so is every hook-only command (see Reserved Bash). A protected action is allowed only while the decision is `PROCEED`, `RUN_VERIFICATION` or `COMPLETE`.
- **Managed project** = enabled, tracked by the hook mode (`OPTIMIZER_MODE` unset, `always-on` or `managed`, or opted in), and with at least one approved check. Elsewhere protected actions are advisory and allowed.
- **Controller-started tasks.** `gate --tool T [--input-file TOOL_INPUT.json]` for a protected action in a managed project with no active session calls `startFromPrompt` on the latest hook-captured prompt (prompts that only say `approve check CODE` are skipped). The session keeps the prompt verbatim as R1, with acceptance "Every user-approved project check passes against the final source." and `acceptanceSource: 'project-checks'`. It records the prompt as `origin` and as a user decision, retrieves context and becomes the active session, and the action is denied with the next checkpoint. It is idempotent per prompt, and work under the same prompt after a verified session reopens that session. Reads, control commands and unmanaged projects never open the store, so they start nothing. `gate` never fails for a missing session. If the runtime cannot answer while a session pointer is active, protected actions are denied with "optimizer unavailable" and reads pass; without a pointer it fails open. `start-from-prompt --prompt ID` does the same for a chosen prompt and requires `OPTIMIZER_HOOK_TOKEN`.
- **Verification outcomes.** `verify` adds `outcome` and `phase`. `VERIFIED`: every requirement has current passing evidence. `NEEDS_HUMAN_REVIEW`: a requirement maps to no check, a critical human question is open, or the session escalated without a failing check. `FAILED`: a check's latest current evidence failed (phase `recovery`, or `reconsidering` once the failure streak pauses). Otherwise `INCONCLUSIVE` (stale context, missing evidence, timeouts). Exhausted reconsideration or challenge budgets record phase `blocked`.
- **Stop budget.** `blocked --reason TEXT [--session ID]` (hook token required) records phase `blocked`. `decide` then returns `BLOCK_ACTION` and the gate denies protected actions until the next checkpoint command records a new phase.
- **Overhead.** `gate`, `decide`, `block` and each phase sync appear in `metrics` as `gate`, `decide`, `block` and `phase`. In-process `evaluate` measured about 0.001 ms per call and `classifyBash` about 0.002 ms. A CLI `gate` process takes about 0.3 s wall time on a development machine, almost all of it Node.js startup.

- **User proof for enable and disable.** CLI `enable` and `disable` apply directly only when stdin and stdout are TTYs (a human at a terminal). Otherwise they store a `pendingChange` (`enable` with its checks, or `disable`) with a random four-hex-digit code and return `approve enable|disable CODE`. Only a token-checked captured prompt quoting that phrase applies it; a disabled project still accepts that one prompt, and a wrong code applies nothing. The library functions `enableProject` and `disableProject` remain direct for operator code. The hook's token therefore grants no enable, disable or check change.
- **Globs.** Any unquoted word with `*`, `?`, `[` or a brace expansion (`{a,b}`, `{1..3}`) makes the command protected. A glob in command position, or a glob together with a hook-only word, is reserved. `cd`/`pushd` targets are resolved through symlinks and must stay inside the root. `optimizer` commands need exactly one `--project` (the CLI refuses repeats) and no earlier `cd`. `uniq` is no longer a read.
- **Reserved Bash.** Checked on the command with every quote and backslash removed. Any Bash command that mentions `.optimizer` (outside `.optimizer/drafts/`), `optimizer-layer/projects` (the per-user store and hook tokens) or `optimizer-claude-hook` is reserved and denied, including reads. Any spelling that invokes the runtime CLI (`optimizer`, a path ending in `/optimizer`, or `cli.ts`/`cli.js`) followed anywhere by `prompt`, `enable`, `disable`, `start-from-prompt`, `blocked` or `run` is reserved too. The match fails safe: such a word as an option value also reserves the command.
- **Replacing a controller-started contract.** `start --replace` over an unfinished controller-started session must keep that session's R1 verbatim as a requirement statement (it may add requirements). The replacement inherits the `origin`, so the rule holds for later replacements too.
- **Execution after review.** Once the phase is `executing` or `recovery` under an accepted contract, a stale project digest alone no longer denies protected actions. The gate keeps the reviewed snapshot, and fresh context is required only for verification. Clarification, challenges, pauses and blocks still deny.
- **Fail closed.** In a managed project, if the gate or classifier throws, protected actions are denied even before a task starts. Only unmanaged or untracked folders fail open. The hook finds the root by preferring the nearest ancestor with an enabled per-user record over a nearer bare `.optimizer` directory. Bash `optimizer` commands must pass `--project` resolving to the tracked root. `cd`/`pushd` count as reads only to a literal directory inside the root. Git is a read only when the shell's cwd is the root, no earlier segment changed directory, no `-C`/`--git-dir`/`--work-tree` is given, and the root is not shaped like a bare repository (`HEAD` and `objects` without `.git`). A runtime mention the tokenizer cannot read exactly (for example `optimizer $a$b`) is reserved.
- **Agent `start`.** In a managed project, a CLI `start` without a protected replacement must keep the latest hook-captured prompt verbatim as a requirement statement. The library `Runtime.start` is operator code and is not restricted. Replacing an unreadable session fails closed.
- **Work after verification.** `verified` is terminal: the session keeps its result, evidence and events, and later edits never reopen it. A protected action after verification starts a new session from the latest captured prompt, with its own context, review and verification; Stop blocks until that new session verifies. On a verified session `retrieve`, `assess`, `resolve`, `review`, `history`, `reconsider` and `check` are refused, while `claim`, `blocked` and `verify` are no-ops that report the recorded result; none appends events.
- **`current`** also returns `phase` and `checkpoint` (the structured decision), so hooks need one runtime spawn per prompt or Stop.

### Managed execution

`optimizer run --project P --prompt-file F [--max-turns N] [--timeout-ms N] [--claude PATH] [--hook PATH]` (`managed.ts`) requires a managed project, rejects an unfinished active session, and refuses to start when `OPTIMIZER_MANAGED_RUN` (set for the agent it launches) or `OPTIMIZER_HOOK_TOKEN` is in its environment. It records F as a `capturedBy: 'controller'` row whose MAC uses a distinct role. Such `run:` rows identify the request but carry no human authority: they cannot resolve human questions, the gate never starts a contract from them, and approval codes in them are ignored. It calls `startFromPrompt` before launch and writes a 0600 settings file whose hooks carry `OPTIMIZER_MODE='managed'` (treated as tracked and enforced). It then runs `claude -p` without a shell (prompt on stdin, `--settings`, `--append-system-prompt`, `--max-turns`, `--output-format json`, plus whitespace-split `--claude-args=...` minus metacharacters and run-owned flags, killed at the timeout), runs `verify` itself, and prints the outcome with the agent's exit code, `turns` and `usage` exactly as Claude Code reported them (else `null`), and timings. It exits non-zero unless the outcome is `VERIFIED`. Only runs it launches are covered.

### Decision model and experiences

There is no learned model yet. `decision-model.ts` defines `DecisionModel` (`{version, rank(features, actions)}`) and the default `rule-v0.1`, which ranks the `decide()` result first. A model only orders the actions the gate allows. Only `PROCEED` offers a choice (`PROCEED`, `RUN_VERIFICATION`, `RETRIEVE_CONTEXT`); every other decision is mandatory, and `evaluate` never consults a model. `StateFeatures` hold only numbers, booleans and enums (phase, question counts, context completeness and coverage, review state, control, failure streak, reconsideration rounds, check count, last check outcome, time since start, event count), never goal or prompt text.

Checkpoint commands and gate evaluations append a `decision.recorded` event whenever the (phase, decision) pair changes, so repeated identical gate queries add nothing. `verify` outcomes and transitions to `blocked` append `decision.outcome`, which covers every decision since the previous outcome with verification progress, `goalSatisfied`, elapsed time since each decision, and `additionalTokens: null` (token usage is never invented). `OPTIMIZER_SHADOW_MODEL=prefer-retrieve` records a built-in candidate's ranking in `shadow` beside the real choice; it never changes decisions or the gate, and it is off by default. `experiences [--session ID]` exports the experiences joined with their outcomes as a JSON array.

Limitations: plugin mode cannot stop an agent running without the hooks, cannot see writes hidden inside allowlisted programs, pauses only at tool boundaries, and a same-user process can still modify state outside the hooks. Only Edit, Write, MultiEdit, NotebookEdit and Bash reach the gate; other tools (MCP servers, web tools) are not gated. Edits outside the project root are not gated. The Read tool can read any file, including the per-user store.
